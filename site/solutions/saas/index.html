Scripts and AI browser agents create accounts from hosting networks, redeem the launch code and start generating on free credit. Each line is one decision BotRampart made in your app, with the route, the signal that decided it and the tier the session held.

Where it stops

Every account costs a pass. Every pass buys less.

A sign-up costs 150 units and a promo redemption 300, so the free credit a farm is after costs it human checks, and each repeat check buys half the last. Generation is metered per account across all its sessions, so an agent looping on free credit hits the hourly ceiling.

How budgets and grants work

The policy

Price the free things. Cap them per account.

A policy file for a SaaS product

Sign-up and redemption carry a price; generation carries a small one, and your app reports the true cost of each call afterwards in a BR-Cost header. The account ceiling holds an account to 6,000 units an hour however many sessions it opens. The decision model's answers act live: a cohort read as fake sign-ups is asked for a step-up, and one read as resource exhaustion is served a cheaper response.

  • Signed-in users refill three times faster, so paying customers do not feel the meter.
  • Simulate a change and see how many signed-in sessions it would newly affect.
  • Every field here is in the policy reference.

botrampart.policy.yaml · SaaS product

path_classes:
  - { name: general, match: ["/*"], cost: 1, min_tier: 0 }
  - { name: signup, match: ["POST /api/signup"], cost: 150, min_tier: 1 }
  - { name: promo, match: ["POST /api/promo/redeem"], cost: 300, min_tier: 2 }
  - { name: generate, match: ["POST /api/generate*"], cost: 10, min_tier: 1 }
budget: { refill_per_min: 20, burst: 300, identified_multiplier: 3, account_ceiling_per_hour: 6000, max_concurrent: 3 }
mint: { ip: 10, prefix: 30, asn: baseline_x3, ja4: baseline_x5 }
risk_score:
  - { when: "signals.automation_flag", add: 4 }
  - { when: "signals.pow_ms_implausible", add: 1 }
  - { when: "session.network_changes_1h >= 5", add: 2 }
  - { when: "net.asn_class == 'hosting' && request.path_class == 'signup'", add: 3 }
rules:
  - { id: not-a-browser, when: "!ua.is_browser", then: block }
  - id: signup-farm
    when: "ai.intent == 'fake_signups' && ai.confidence >= 0.7 && request.path_class == 'signup'"
    then: "challenge(step_up)"
  - id: signup-risk
    when: "request.path_class == 'signup' && risk.score >= 4"
    then: "challenge(human)"
  - id: credit-burn
    when: "ai.intent == 'resource_exhaustion' && request.path_class == 'generate'"
    then: degrade
  - id: over-budget
    when: "session.credits < request.cost"
    then: "challenge(next_tier) || throttle"
  - { id: default, when: "true", then: allow }

Built for free tiers

Three parts doing the work. All in the file above.

Account ceiling

Spend follows accounts.

Cap spend at 6,000 units an hour across every session of one signed-in account, so opening more tabs or agents buys no more credit.

BR-Cost

Bill true cost.

Set BR-Cost on a generation response once you know its token count, and the SDK settles the difference on the session.

Live directives

Farms get escalated.

Ask a cohort the decision model reads as fake sign-ups for a step-up, and serve a cheaper response to one read as resource exhaustion.

Questions from SaaS teams

Before the next launch.

Does it slow sign-up down for real users?

The proof-of-work runs in a Web Worker while the person fills in the form, so the request is ready by the time they press the button. A human check appears only when the risk score passes your threshold.

Generation costs vary per call. How is that metered?

Give the generate path a small fixed price, then set BR-Cost on the response once you know the real cost. The SDK charges or refunds the difference on the session and removes the header.

Can an AI agent acting for a paying customer still work?

Yes. Once the customer signs in, their sessions refill three times faster and spend against the account's hourly ceiling, so an agent working for them runs inside a known budget instead of being blocked.

How do we avoid challenging customers by mistake?

Run any rule with mode: log first, and simulate a policy change against the last 24 hours: the result counts the signed-in sessions it would newly affect before you publish it.
