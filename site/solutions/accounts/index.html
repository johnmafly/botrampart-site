Where it stops

Tier 2 stops the list. Tier 3 stops the takeover.

A login attempt costs 100 units, so a proof-of-work buys three tries and a human check thirty, then fifteen. With the daily ceiling one session makes at most about 350 attempts a day, so a list of a million passwords needs some 2,800 sessions, and every fresh session is rationed per network. A session that does get in meets a step-up before it changes the email, the password or a payee.

How budgets and grants work

The policy

Price the attempt. Step up the change.

A login policy file

The login, the password reset, the code sender and the account settings each carry a price. Mint buckets are tight because stuffing lists arrive through proxy pools. The five-minute loop's answers act live: when the decision model reads the login cohort as credential stuffing, every attempt in it is asked for the human check.

  • Attach the login ID with br.identify after sign-in; BotRampart keeps only a keyed hash of it.
  • Stage a new rule with mode: log for a week before it enforces.
  • Every field here is in the policy reference.

botrampart.policy.yaml · login

path_classes:
  - { name: general, match: ["/*"], cost: 1, min_tier: 0 }
  - { name: login, match: ["POST /login", "POST /api/password/reset"], cost: 100, min_tier: 1 }
  - { name: otp, match: ["POST /api/otp/send"], cost: 500, min_tier: 2 }
  - { name: account_change, match: ["POST /api/account/*"], cost: 20, min_tier: 1 }
budget: { refill_per_min: 20, burst: 300, identified_multiplier: 3, account_ceiling_per_hour: 2000 }
mint: { ip: 10, prefix: 30, asn: baseline_x3, ja4: baseline_x3 }
risk_score:
  - { when: "signals.automation_flag", add: 4 }
  - { when: "signals.pow_ms_implausible", add: 2 }
  - { when: "session.network_changes_1h >= 5", add: 2 }
  - { when: "net.mint_pressure", add: 2 }
  - { when: "net.asn_class == 'hosting'", add: 1 }
rules:
  - { id: not-a-browser, when: "!ua.is_browser", then: block }
  - id: takeover-guard
    when: "session.identified && request.path_class == 'account_change' && risk.score >= 3"
    then: "challenge(step_up)"
  - id: stuffing-cohort
    when: "ai.intent == 'credential_stuffing' && ai.confidence >= 0.7 && request.path_class == 'login'"
    then: "challenge(human)"
  - id: risk-5
    when: "risk.score >= 5 && request.path_class == 'login'"
    then: "challenge(human)"
  - id: over-budget
    when: "session.credits < request.cost"
    then: "challenge(next_tier) || throttle"
  - { id: default, when: "true", then: allow }

Account ceiling

Cap spend at 2,000 units an hour across every session of one login, so a takeover running ten sessions gets no more than the owner does.

Questions from fraud and identity teams

Before the next leaked list.

Does this replace our MFA?

No. BotRampart decides before your password check runs and prices the attempt; MFA proves the person after it. Step-up adds an email link, a sign-in or a passkey for risky account changes, beside the factors you already use.

Stuffing runs through residential proxies. Does rationing by IP help?

The address is a bucket, never the identity. New sessions are counted per IP, per /24 or /48 prefix, per ASN and per TLS fingerprint family, and the five-minute loop watches the login cohort as a whole, so rotating addresses does not reset the price.

How does it stop SMS pumping?

Sending a code is its own path class at 500 units, behind the human check. A pass buys six codes, the next three, and refill sends one every 25 minutes, so a script cannot turn your SMS provider into its revenue.

What does BotRampart keep about our customers' logins?

A keyed hash of the login ID, HMAC-SHA256 under a key only you hold, and never the password. No device fingerprint, no keystroke content, and every record stays in your own bucket.
