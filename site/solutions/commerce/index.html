Where it stops

Tier 2 stops the cart bots. Tier 3 stops card cracking.

A headless browser solves the proof-of-work, so tier 1 alone does not stop a scalper. What stops it is the price: a cart costs 50 units, a pass buys a fixed grant that halves on every repeat, and a new session to start over is rationed per network.

How budgets and grants work

The policy

Price the cart. The ladder does the rest.

A storefront policy file

Path classes put a price on the cart, checkout and gift-card routes. Mint buckets are tighter than the defaults, because a drop is when cookie-discarding farms show up. The five-minute loop's answer acts live: when it reads a cohort as inventory abuse, its proof-of-work gets four times harder.

  • Declare the drop as an event, and the loop reads the spike as expected traffic.
  • Simulate the file against yesterday's traffic, publish it for the drop, roll it back after.
  • Every field here is in the policy reference.

botrampart.policy.yaml · storefront

path_classes:
  - { name: general, match: ["/*"], cost: 1, min_tier: 0 }
  - { name: cart, match: ["POST /api/cart*"], cost: 50, min_tier: 1 }
  - { name: checkout, match: ["/api/checkout*"], cost: 20, min_tier: 1 }
  - { name: giftcard, match: ["POST /api/giftcard/balance"], cost: 100, min_tier: 2 }
budget: { refill_per_min: 20, burst: 300, max_concurrent: 4 }
mint: { ip: 10, prefix: 40, asn: baseline_x3, ja4: baseline_x3 }
risk_score:
  - { when: "signals.automation_flag", add: 4 }
  - { when: "signals.pow_ms_implausible", add: 2 }
  - { when: "signals.no_input_after_30_requests", add: 2 }
  - { when: "net.mint_pressure", add: 2 }
rules:
  - { id: not-a-browser, when: "!ua.is_browser", then: block }
  - id: card-cracking
    when: "request.path_class == 'giftcard' && risk.score >= 3"
    then: "challenge(step_up) || block"
  - id: drop-risk
    when: "risk.score >= 5 && request.path_class in ['cart', 'checkout']"
    then: "challenge(human)"
  - id: inventory-abuse
    when: "ai.intent == 'checkout_or_inventory_abuse' && ai.confidence >= 0.7"
    then: "pow(4)"
  - id: over-budget
    when: "session.credits < request.cost"
    then: "challenge(next_tier) || throttle"
  - { id: default, when: "true", then: allow }

Built for drops

Three parts doing the work. All in the file above.

Path prices

Carts cost more.

Price the cart at 50 units and a product page at 1, so a session hoarding stock runs dry while a shopper browsing for an hour never notices.

Mint buckets

Restarts are rationed.

Count new sessions per IP, /24, ASN and TLS fingerprint family, so a farm that throws cookies away meets a harder proof-of-work on every restart.

Gift-card step-up

Every guess costs.

Put balance checks at tier 2 with a step-up on risk, so a human pass buys 30 guesses, the next one 15.

Integration

In the storefront, or at the edge in front of it.

Each path verifies the same __br_s cookie and answers with the same challenges. Pick the one where your cart traffic already flows.

  • Available

    Express, Fastify and Next.js storefronts. Decides inside the process that serves the cart API, with no network call per request.

Questions from commerce teams

Before the next drop.

Do real buyers see a puzzle when the drop opens?

Most never do. The proof-of-work runs in the background while the product page loads, and the human check appears only when a session's risk score passes your threshold or it overspends. When it does appear, it works with a keyboard and a screen reader.

What if the bots pay a solver service?

The policy assumes they do. A pass buys credit, not clearance: 3,000 units the first time, half that the next, and each new session to start over is rationed per network. Paying for passes buys a bounded number of carts, not the drop.

Our product pages are cached on a CDN. Does that matter?

The browser SDK starts a session from a cached page and protects the cart and checkout APIs behind it. With the Cloudflare Worker or CloudFront adapter, the cookie is checked before the cache answers, too.

How do we get ready for a known drop?

Declare the drop as an event so the five-minute loop reads the spike as expected, publish a stricter policy version for the window after simulating it, and roll back to the previous version when the drop ends.
