BotRampart checks each request before your app does the work. Put it inside your Node app today, or in front of it at your edge. Every option runs in your infrastructure or your cloud account: no vendor proxy sits in the path, and no one else sees your traffic.

Integration options

Each option does the same job on the wire: it reads the session cookie __br_s, charges the request against the session's budget, and answers with a challenge when the budget runs out. Pick the one that matches where your traffic already flows.

  • Available

    Node backend SDK

    Express · Fastify · Next.js

    Visitor→App + SDK→Handlers

    Runs inside your app process, in front of your handlers. It serves the browser script and challenge routes under /_br on your own origin, verifies __br_s with your site keys and syncs counters with Core every 5 to 10 seconds. It stays light: it keeps no aggregated visitor metrics, baselines or history, which Core builds.

What every option shares

The integration is an HTTP contract, defined in full in the OpenAPI spec. Whatever sits in front of your handlers, these are the parts your visitors and your logs see:

PartWhat it is
__br_sOne first-party cookie, set HttpOnly by your own server and signed with your site key. A random session ID, a tier and an expiry; no fingerprint.
/_br/*The browser script and the challenge routes, served on your own origin: the SDK routes.
BR-Challenge: v1Marks a challenge (403) or throttle (429) answered instead of your app's response.
BR-Sid, BR-DecisionSet on every response that passes through. Your edge logs them and strips them.
BR-CostYour app sets it when a response's true cost is known only afterwards; the difference is settled on the session.
CoreOne small service you run on Cloudflare Workers or as one container. Challenges, policy, counters and the decision log in your bucket.

Start in observe mode

Observe mode decides every request, logs the decision and lets it through, so you see what BotRampart would have done before it does anything. You need:

  • A Node app on Express, Fastify or Next.js.
  • Somewhere to run Core: a Cloudflare account (Workers Paid starts at $5 a month{{c:cf-workers-price}}) or any host that runs one container. Recommended: 256 MB of memory. No database server.
  • An S3-compatible bucket: Cloudflare R2, Amazon S3 or MinIO.
  • Optional: a key for a decision-model provider, or a self-hosted model. Without one, the five-minute loop is off and everything else works.

  1. Configure Core

    Core listens on port 8787. It reads where the lake is and which decision model to use from its environment, and its keys from your secret store. Configuration explains each setting.

    SettingExampleMeaning
    BR_LAKE_URLs3://acme-botrampart/br/v1/Where the lake lives
    BR_DECISION_PROVIDERoffoff, gemini, openai, or a self-hosted model
    Secret br_keyssite keysSigns session tokens and puzzles
    Secret lake_writerbucket credentialLets Core write the lake

  2. Mount the backend SDK in observe mode

    Mount it at the root of your app, in front of your handlers, so every route gets a path class by default. Set site, secretsFile, core and mode: "observe"; Wire it in lists every setting. It serves the /_br routes and sets BR-Sid and BR-Decision on every response.

  3. Add the browser script

    One script tag, served from your own origin by the backend SDK, so no third-party domain can change the code your visitors run. That is the lesson of the 2024 Polyfill.io incident, when a CDN script under new ownership served malware to more than 100,000 sites.{{c:polyfill}}

    Your page templategetSdkScript

    <script src="/_br/sdk.js" data-site="site_123" async></script>

  4. Check the session

    Open your site and ask what the browser holds. A first visit is tier 0; a moment later the proof-of-work has run in the background and the session is tier 1.

    In the browser, from your own origingetSessionStatus

    GET /_br/status

{ "tier": 1, "expiresAt": 1794825300, "sessionEndsAt": 1795428300, "tierExpiresAt": {}, "identified": false }

  5. Watch, then simulate

    Within the first hour the decision log in your bucket shows spend by path class, the sessions that would have been challenged and why, and path costs suggested from how long each path takes to answer. Replay a changed policy against that traffic before you enforce anything:

    Replay a policy against the last 24 hourssimulatePolicy

    curl -X POST "http://localhost:8787/v1/policy/simulate" \
  -H "Authorization: Bearer $BR_CONSOLE_TOKEN" -H "Content-Type: application/json" \
  -d @draft-policy.json

{ "challenged_share_current": 0.004, "challenged_share_draft": 0.012, "signed_in_affected": 0,
  "summary": "Would have challenged 1.2% of sessions against 0.4% today, none of them signed in." }

  6. Enforce tier 1

    Switch mode to "enforce" with the default policy. Ordinary browsing stays inside the refill rate and sees nothing. Clients that cannot run JavaScript keep reading general pages on their 30-unit allowance and are asked for a proof-of-work on costly paths. Keep the five-minute loop in shadow until its answers match what you would have done.
