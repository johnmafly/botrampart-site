Build · 02 · integration guide

Wire it in. Read the wire.

The Node backend SDK runs in front of your handlers in Express, Fastify or Next.js. What it does is the same in all three, and all of it is HTTP: the routes it serves, the headers it sets, the challenges it answers with. Every exchange is in the OpenAPI spec, and each sample names its operation.

The SDK packages are not on a public registry yet, so this guide shows no install command and no package import. It shows the contract every adapter implements, which is also what you test against. For a guided setup, generate an install prompt for your coding agent.

Settings

Mount the backend SDK once, at the root of your app and in front of your route handlers, so every route gets a path class by default. It reads these settings; Configuration has the full list.

SettingDefaultWhat it does
siterequiredSite ID; keys, policy and lake partitions are per site.
secretsFilerequiredHMAC keys that sign the session cookie and proof-of-work puzzles, so tier 1 works with Core unreachable. Alternative: tokens signed by Core with Ed25519, at one Core call per new session.
corenoneCore's URL. Without it the SDK runs alone: tiers 0 and 1, local budgets, the policy file on disk.
store"memory"Where budgets live. In memory, spend across instances is reconciled at each sync, so overspend is bounded by one sync interval; Redis or Valkey makes it exact.
mode"observe""observe" decides and logs every request and lets it through; "enforce" applies the decisions. Start every install in observe mode.
onCoreDown"static"Tokens still verify, budgets still count, the last policy still applies. Tier 2 cannot be served, so rules that require it fall back to throttle.

The script is the version bundled with the backend SDK, served with Cache-Control: public, max-age=31536000, immutable and BR-SDK-Integrity, the Subresource Integrity hash of the published release.

Sync with Core

Each instance sends its counters to Core every 5 to 10 seconds and receives policy, directives and revocations in the same call. No per-request record leaves your app; session IDs travel as hashes.

The SDK is kept light so it never slows your app: it holds each live session's budget and a short buffer of counters until the next sync, then drops them. It keeps no aggregated visitor metrics, baselines or history; Core builds those.

Challenges

A protected route that cannot be paid for answers 403 (or 429 with Retry-After for a throttle) instead of your app's response, with the header BR-Challenge: v1. With autoRetry on, the browser script runs the challenge and retries the request once when retry is true.

Response headers

HeaderSet byMeaning
BR-SidThe SDK, on every responseThe first 12 hex characters of SHA-256 of the session ID, never the ID itself.
BR-DecisionThe SDK, on every responseallow, log, challenge:pow, challenge:human, throttle, block or degrade.
BR-CostYour app, on its own responseThe request's true cost in units. The SDK settles the difference from the path class's cost and removes the header.
BR-ChallengeThe SDKv1 on a challenge or throttle response.

Signing in

Once your user authenticates, attach their login ID to the session with the backend SDK's br.identify. BotRampart stores only a keyed hash of it, HMAC-SHA256(site_uid_key, login ID). Signed-in sessions refill three times faster, are exempt from network mint pressure, and their spend is also summed per account, so one account cannot fan out over many cookies.

For EU sites, run signals: "minimal" or "off" and document the cookie as a security measure. France's regulator says anti-robot measures whose sole purpose is securing the site or its sign-in need no consent;{{c:cnil-antibot}} the cookie and signals must then be used for nothing else. This is an engineering reading, not legal advice.

The policy file

One versioned YAML file per site, kept in Git; the console shows it read-only. Rules are evaluated in order and the first match wins. Conditions are written in CEL and compiled by Core into a typed condition tree, which every SDK evaluates with the same small interpreter and the same conformance suite.

botrampart.policy.yaml (abridged)putPolicy

version: 12
path_classes:
  - { name: static,   match: ["/assets/*", "*.css", "*.js", "*.png"], cost: 0,  min_tier: 0 }
  - { name: general,  match: ["/*"],                                  cost: 1,  min_tier: 0 }
  - { name: search,   match: ["/api/search*"],                        cost: 5,  min_tier: 1 }
  - { name: login,    match: ["POST /login"],                         cost: 10, min_tier: 1 }
  - { name: checkout, match: ["/api/checkout*"],                      cost: 20, min_tier: 1 }
budget:
  refill_per_min: 20
  burst: 300
  provisional: 30
  grants: { pow: 300, human: 3000 }
  grant_decay: 0.5
  identified_multiplier: 3
mint: { ip: 20, prefix: 60, asn: baseline_x5 }
rules:
  - { id: verified-bots, when: "net.verified_bot in ['search_engine', 'monitoring']", then: allow }
  - { id: not-a-browser, when: "!ua.is_browser || ua.browser_age_years > 3", then: block }
  - { id: risk-5,        when: "risk.score >= 5", then: "challenge(human)" }
  - { id: ai-escalation, when: "ai.attack >= 0.9 && ai.confidence >= 0.7 && request.path_class in ['search', 'login']",
                         then: "log" }      # the decision model runs in shadow: it logs, never acts
  - { id: over-budget,   when: "session.credits < request.cost", then: "challenge(next_tier) || throttle" }
  - { id: default,       when: "true", then: allow }
FieldsExamplesFrom
request.*path_class, cost, methodThe request and your path classes
session.*tier, age, credits, identified, network_changes_1hThe cookie and the local budget
ua.*is_browser, family, browser_age_yearsUser agent, parsed against a bundled release table
net.*mint_pressure, verified_bot, country, asn_classMint buckets, crawler verification
signals.*automation_flag, no_input_after_30_requestsThe browser script, checked on the server
risk.score0 to 10A visible scorecard in the same file, every line editable
ai.*attack, risk_level, intent, action, confidenceThe five-minute loop, with expiry (logged only)

Actions: allow, log, challenge(pow | human | next_tier), pow(multiplier), throttle, block, degrade (tell your app to serve a cheaper response) and add_risk(n). A rule can run as log for a week before it enforces. Publishing creates an immutable version that SDKs pick up at the next sync; rollback is publishing the previous one. Always simulate first (example).

Logs and headers

The cookie is a bearer credential and must never reach a log. Log BR-Sid and BR-Decision at your edge instead, then strip them. A path that shows up in your access logs without BR-Decision is a route the SDK does not cover.

nginx: log the decision, then strip the headers

log_format br escape=json '{"time":"$time_iso8601","path":"$uri","status":$status,'
  '"br_sid":"$upstream_http_br_sid","br_decision":"$upstream_http_br_decision"}';
proxy_hide_header BR-Sid;
proxy_hide_header BR-Decision;

Edge cases

SituationWhat to do
Publicly cacheable pagesThe SDK never sets the cookie on a response marked publicly cacheable, so your CDN can still cache it; the browser script starts the session through /_br.
An API on another originSet the cookie Domain for sibling subdomains, or send the token in a header for cross-origin calls.
WebSockets and streamsVerified at the upgrade, charged by connection time, re-verified on a timer.
Webhooks, partner APIs, mobile appsAdd a rule that allows requests authenticated by your own API key or signature before the over-budget rule.
SDK error or missing configurationFail mode per route: open for content, closed for login, sign-up and checkout.
Clock skew and key rotation60 seconds of tolerance; two keys accepted during rotation.

Testing your integration

  • Run CI and staging in observe mode, and assert on the BR-Decision header of your app's responses in your own tests, before the edge strips it.
  • Replay a changed policy against production traffic with simulatePolicy before every publish.
