Detection

A script can fake a browser. It can’t fake being bored.

The browser SDK reports how the page is used; your server checks it. Automation leaves traces a user-agent string can't hide: a flag the browser itself raises, thirty pages without a single tap or keystroke, a proof-of-work finished faster than the hardware allows.

01 · Browser risk signals

What the browser admits

The automation flag browsers expose, the proof-of-work solve time, focus and visibility changes, viewport size class.

02 · Abnormal UI behaviour

How the page is used

Counts of pointer, touch and key events and time to first input. No input after 30 requests is a pattern people don't make.

03 · Checked server-side

Decided where it can't be tampered with

Signals are scored by your policy inside your app, against a session cookie signed with your key. Verifying it and charging the session took 1.79 µs at the median in our benchmark.{{c:exp-verify}}

04 · No fingerprinting

Counts, never identities

No canvas, WebGL or audio fingerprints, font lists, stable device IDs or keystroke content, in any mode.

Autopilot challenges · custom policies

It escalates by itself. You decide where the line is.

You don't pick a challenge per route. When a session looks wrong or overspends, BotRampart asks for the next tier up, and a session that keeps coming back climbs the ladder. One check per session with no limit behind it only adds latency, not limits:{{c:anubis-throughput}} here each repeat costs more.

  1. Tier 0

    Provisional

    First visit. General pages only, on a small allowance.

  2. Tier 1

    Invisible proof-of-work

    The browser does a few small sums in the background. Plain HTTP clients can't.

  3. Tier 2

    Accessible human check

    One tick, scored on how it was ticked. Works with a keyboard and a screen reader.

  4. Tier 3

    Step-up

    An email link, a passkey or a challenge widget, for the moment a session must prove a person is behind it.

Policies are a file you own

Weights, thresholds and rules live in one YAML file in your repository. Conditions are CEL expressions over request, session and signal fields. Simulate a draft against yesterday's traffic, publish it as a new version, roll it back in one step.

  • challenge(next_tier) is the autopilot: it asks for one tier above what the session holds.
  • Rules run in your order. Nothing acts that you didn't write down.
  • New rules can run in mode: log first and act on nothing.

Policy reference →

botrampart.policy.yaml · excerpt of version 12

risk_score:
  - { when: "signals.automation_flag", add: 4 }
  - { when: "signals.no_input_after_30_requests", add: 2 }
  - { when: "signals.pow_ms_implausible", add: 1 }
rules:
  - id: not-a-browser
    when: "!ua.is_browser || ua.browser_age_years > 3"
    then: block
  - id: risk-5
    when: "risk.score >= 5"
    then: "challenge(human)"
  - id: over-budget
    when: "session.credits < request.cost"
    then: "challenge(next_tier) || throttle"
  - { id: default, when: "true", then: allow }

Integrations

Fits where your traffic goes. In your app or at your edge.

Backend SDKs for Node, Python, Ruby, PHP, Java and Go decide inside your app. Edge adapters decide before traffic reaches your origin. Both share one session budget and one Core.

  • In your app

    Backend SDKs

    Express, Fastify, Next.js, Django, FastAPI, Rails, Laravel, Spring Boot and Go. No network call per request.

  • In the browser

    Browser SDK

    One script tag, served from your own origin at /_br/sdk.js. Runs the proof-of-work and reports signals.

  • Your cloud

    Core

    Syncs counters and writes the log. Runs on Cloudflare Workers or as one container.

  • Edge

    nginx module

    Decisions in front of any backend, configured in nginx or ingress-nginx.

  • Edge

    Cloudflare Worker

    Runs at Cloudflare's edge in your own account, in front of your origin.

  • Edge

    CloudFront Lambda@Edge

    For sites served through Amazon CloudFront, on viewer request and response.
