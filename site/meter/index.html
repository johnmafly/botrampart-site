The meter · how it works

Every session gets a budget. Every path gets a price.

That's the whole mechanism. This page walks through it: what a session is, what things cost, how credit comes back, why a pass buys less each time, and what the meter can't see.

The idea

Bot defense usually asks one question: is this client a bot? That question has become expensive to answer and cheap to fool. Image puzzles are solved by published models,{{c:recaptcha-solved}} solver services sell passes by the thousand,{{c:solver-prices}} and residential proxies make an IP address a disposable identity at prices starting near a dollar a gigabyte.{{c:proxy-prices}}

BotRampart asks a different question: what has this session spent? Every session holds credit. Every path has a cost. Ordinary use refills faster than it spends; heavy use runs out and has to earn more by passing a challenge, and each repeat earns less. A pass buys credit, never a clearance.

Nobody is labelled a bot, so there is no verdict to dispute. Anyone can check the arithmetic, so every decision can be explained.

A session’s life

Identity is one first-party cookie, __br_s, set by your own server with HttpOnly and signed with your site key. It carries a random session ID, its tier and its expiry; no device fingerprint. The token lives 30 minutes and is renewed while in use, inside a session of at most seven days, so a revoked session stops working within half an hour even on an app instance that missed a sync. That lifetime follows Cloudflare's own guidance for its clearance cookie, 30 minutes by default and 15 to 45 recommended.{{c:cf-passage}}

Because your server sets the cookie, page scripts cannot read it, and Safari's rule that deletes script-written cookies after seven days without interaction does not apply to it.{{c:webkit-7day}}

Request economics

Each request is charged the cost of its path class before your handler runs. The policy file names the classes; these are the defaults:

Path classExample matchCostLowest tier
static/assets/*, *.css, *.png00
general/*10
search/api/search*51
loginPOST /login101
checkout/api/checkout*201

A session regains 20 units a minute up to a balance of 300, and three times as fast once your app attaches a login ID. When it cannot pay, the over-budget rule asks for the next challenge; when the shrinking grants are spent, it throttles. In code, the whole of it:

on request(session, path_class):
    cost = path_cost[path_class]                     # 0 for static
    rate = refill_per_min * multiplier(session)      # x3 when signed in
    session.credits = min(burst, session.credits + rate * minutes_since_last)
    if session.credits >= cost: session.credits -= cost; return ALLOW
    return over_budget(session)                      # next challenge, else throttle

on challenge passed(session, tier):
    n = passes of this tier by session in the last 24 h
    session.credits += grant[tier] * 0.5 ** n        # 300 / 3,000 / 6,000, halving

This is not a new idea, only a new place for it. GitHub's GraphQL API gives each user 5,000 points an hour and prices each query by the work it implies,{{c:gh-graphql}} Shopify limits its Admin API by calculated query cost,{{c:shopify-cost}} and Cloudflare's complexity-based rate limiting reads a cost your origin returns in a response header.{{c:cf-rl-complexity}} BotRampart applies the same accounting to anonymous browser sessions. Your app can report the true cost of an expensive response in a BR-Cost header, and the difference is settled on the session.

Why a pass buys credit, not clearance

A design that challenges once per session and then waves the session through has a known flaw: once the challenge is solved, latency rises but throughput does not fall.{{c:anubis-throughput}} Tying each pass to a fixed grant that halves on repeat gives every session a hard daily ceiling instead.

With the default policy, one session can spend at most 35,363 units in a day with tiers 0 to 2, and 47,175 once a step-up method is available (not yet): a day of refill, the burst, and every grant until a repeat would buy less than 100 units. At 5 units a search that is about 7,000 to 9,400 searches a day. Someone who wants a million searches a day needs more than a hundred sessions, and new sessions are rationed per network, below. These figures come from the reference implementation this site runs, and a test in the repository checks them.

A challenge is not an economic wall by itself. Solvers charge around $1 to $3 per thousand passes,{{c:solver-prices}} so a paid pass that buys 600 searches adds a fraction of a cent per thousand searches. Challenges do three jobs: they shut out clients with no JavaScript engine, they produce interaction signals, and they meter credit. The ceiling and the mint buckets do the limiting.

Clients that throw cookies away

A client that discards its cookie arrives as a new session every time. If new sessions were free, that client would have unlimited budgets. So every new session starts at tier 0 with 30 units for general pages only, and new sessions are counted per network:

Mint bucketWindowDefaultCatches
Exact IP10 min20 new sessionsOne machine discarding cookies
/24 or /48 prefix10 min60 new sessionsA small block, or an IPv6 host rotating addresses
ASN10 min5 × its own baselineA proxy pool inside one provider
TLS fingerprint family10 min5 × baselineOne automation stack spread over many networks

The response to pressure is a price, not a block: a proof-of-work 1.5 to 10 times harder, then a human check for new sessions on costly paths, and only at an extreme a 429. Sessions that are already established or signed in are exempt, so a café or a mobile carrier's shared address does not lock out the people already using your site. IP addresses are disposable to an attacker, and in one study 60% of residential proxy addresses were seen only once in 90 days,{{c:ipinfo-rotation}} which is why the address is a bucket here and never the identity.

The five-minute loop

Some abuse is invisible one session at a time: a slow scrape spread over thousands of sessions, each under budget. Every five minutes Core merges the counters from your app instances, compares them with each cohort's own baseline for that hour of the week, and turns every number into a named band such as cost_vs_baseline: x6_plus or new_session_share: over_60pct. Free text is removed: paths become your class names, user agents become a family. The result is a small JSON state with nothing a visitor typed in it.

Core then asks a decision model four typed questions about that state: is this automated abuse (yes or no, with a probability), how risky is it (a five-level score), what is it most likely for (scraping, credential stuffing, fake sign-ups, an organic spike), and which is the least intrusive step that would contain it. This follows the guidance Google publishes for its Decisions API: compare numbers in code and pass a named bucket,{{c:gd-guide-code}} and treat input as untrusted.{{c:gd-guide-untrusted}} Google launched that API with Gemini Decision 1 on 11 November 2026{{c:gd-launch}} at $0.10 per million input tokens,{{c:gd-price}} so one site-level question every five minutes costs on the order of a few dollars a month (our estimate at about 1,800 tokens a call). The provider sits behind one interface, and a self-hosted model can replace it so nothing leaves your network.

The answer never acts directly. It becomes fields such as ai.attack and ai.action, with an expiry, and the decision log keeps them beside what your rules did. The model runs in shadow mode only: rules that act on its fields are not available yet, so its answers change nothing. Even then it could only raise a price or lower a cohort's budget, never block or allow a client. Answers are cached on a hash of the bands for up to an hour, so a quiet site asks rarely, and any change in a band is a new question at the next window.

Shadow mode only. The model's answers are logged beside what the rules actually did, so you can set thresholds from your own traffic. Letting a rule act on them is not available yet.

Explaining a decision

Every non-allow decision is written to a decision log in your bucket with a reference such as BR-7F3K2Q, which the visitor sees on the challenge. The log records the rule, the policy version, the budget, the cost and the model answer in force, so "why was this person challenged?" is a lookup, not a reconstruction.

An agent with read-only access to the same log answers in Slack or in the console. It uses named, fixed queries, attaches the query and rows to every answer, and cannot change anything: a person changes the policy file. Free-form SQL, suggested policy changes and email from the agent are not available yet. That separation matters, because stored log text can carry instructions aimed at a model: injected log entries steered LLM log analysis up to 88.2% of the time in one 2026 study.{{c:loginject}}

What it does not do

  • Floods and DDoS. The request reaches your app before it is refused. Keep your CDN or WAF for volume; BotRampart refuses before your handler runs, in about 300 bytes.
  • Cached pages and static files. They never reach your app. The browser SDK still starts a session from a cached page and protects the data APIs behind it.
  • Headless browsers driven by a patient operator. Proof-of-work does not stop them. Budgets ration them: they get bounded throughput per session and sessions are rationed per network.
  • Native mobile apps and partner APIs. They carry no cookie and run no JavaScript. Rules pass requests signed with an API key.
